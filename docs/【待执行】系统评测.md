# 接入 Ragas + Opik 做系统评测（第一期：检索质量）

## Context（背景与目标）

当前操作手册 RAG 系统（FastAPI + 原生 `httpx` 直连 DeepSeek，无 LangChain/LlamaIndex）已有完善的业务日志落库（`intent_logs`/`retrieval_logs`/`llm_call_logs`/`messages.steps`），但**评测能力近乎空白**：仅有 [tests/eval_questions.json](backend/tests/eval_questions.json) 的 10 问召回断言（只标 `expect_doc`/`expect_path_contains`，无黄金答案），[docs/系统评测.md](docs/系统评测.md) 是空文件。

本次目标是引入 **Opik（可观测 + 评测平台）+ Ragas（RAG 评测指标库）**，先打通**检索质量**评测闭环：

- **运行时**：真实会话通过 Opik trace 埋点，把意图识别、检索、生成全链路可视化。
- **离线**：扩展 10 问补黄金答案，用 Ragas/Opik 指标（context_precision/context_recall + recall@k/MRR）跑检索评测，结果写入 Opik Experiment 做版本对比。

**用户已确认的决策**：① Opik 自托管（Docker Compose）；② 扩展 10 问补参考答案；③ 运行时埋点 + 离线评测两者都要；④ 优先评测检索质量。

---

## 方案总览

```
线上运行时（后端 app）
  handle_chat ── intent ── retrieve ── generate      @opik.track 埋点
                                        │
                                        ▼
                          ┌─────────────────────────┐
                          │   Opik 自托管（Docker）    │  trace / dataset / experiment
                          └─────────────────────────┘
                                        ▲
离线评测（backend/eval/ 脚本）              │
  golden_dataset.json ──► retriever.search ──► Ragas 指标 + recall@k/MRR ──► Opik Experiment
```

关键设计原则：
1. **不引入 LangChain 到运行时代码**：Ragas 只在离线评测脚本里使用（它会拉入 `langchain-core` 作为依赖，但仅限 eval 环境）；线上 app 仍保持原生 `httpx`。
2. **埋点可开关、可降级**：Opik 未部署/配置时，埋点完全 no-op，不影响现有功能与 CI 测试。
3. **确定性指标与 LLM 判断指标分层**：recall@k/MRR 用纯 Python 算（无需 LLM、零成本、稳定）；context_precision/context_recall 用 Ragas（需 judge LLM + embedding）。

## Part A — Opik 自托管部署

**采用 Opik 官方 docker-compose，独立 compose 项目运行，不并入现有 [docker/docker-compose.yml](docker/docker-compose.yml)。**

原因：现有 compose 已占用宿主机 MySQL 3306 / Redis 6379，而 Opik 自带 MySQL/Redis/ClickHouse，直接合并会端口冲突。独立项目 + 容器网络隔离，仅向宿主机暴露 Web UI 与 API 端口。

- 部署入口：`git clone https://github.com/comet-ml/opik && cd opik/deployment/docker-compose && docker compose up -d`
- UI：`http://<host>:5173`，API 后端默认 8080（SDK 的 `OPIK_URL_OVERRIDE` 指向 `http://<host>:5173/api`，以官方文档为准）。
- **资源要求**：含 ClickHouse + MySQL + Redis + Java 后端 + Python worker + 前端，建议 ≥8G 内存；与现有 Milvus（192.168.0.215）可同网段部署。
- 可选：把官方 compose 固化一份到 `docker/opik/docker-compose.yml` 便于版本锁定（本次先以官方仓库方式跑通，固化可作为后续项）。

## Part B — 依赖与配置

### 依赖（[backend/pyproject.toml](backend/pyproject.toml)）

新增可选依赖组，避免污染线上运行环境：

```toml
[project.optional-dependencies]
eval = [
    "opik>=1.8,<2",
    "ragas>=0.3,<1",
]
```

- `opik` 也需进入**主依赖**（用于运行时埋点），建议直接加到主 `dependencies` 列表：`"opik>=1.8,<2"`。
- **Python 3.13 风险**：Ragas 官方推荐 3.12，3.13 为实验性（NumPy wheel 可能编译失败）。预案（二选一，见「风险」节）：
  - 若 3.13 装 `ragas` 失败 → 用 `uv venv -p 3.12` 建独立评测环境；
  - 或检索质量层切到 **Opik 原生 `ContextPrecision`/`ContextRecall`**（无 Ragas 依赖，同样指向 DeepSeek），Ragas 留作后续生成质量扩展。

### 配置（[backend/app/core/config.py](backend/app/core/config.py)）

在 `Settings` 新增（`.env` 同步补到 `.env` 与 `.env.example`）：

```python
# ---- Opik ----
opik_enabled: bool = False          # 总开关，False 时埋点 no-op
opik_url: str = ""                  # 自托管地址，如 http://<host>:5173/api
opik_project: str = "manual-rag"    # 项目名
opik_api_key: str = ""              # 自托管可留空
```

在 [main.py](backend/app/main.py) 的 `lifespan`（约 32-98 行）里，服务初始化前增加 `_setup_opik()`：`opik_enabled=True` 时才 `opik.configure(url_override=..., project_name=...)`，并 `try/except` 包裹，Opik 不可用时仅告警不阻断启动。

## Part C — 运行时埋点（Opik tracing）

复用现有全局单例，埋点只加装饰器/上下文管理器，**不改业务逻辑**。三处落点：

1. **检索** — [backend/app/rag/retriever.py](backend/app/rag/retriever.py) 的 `ManualRetriever.search()`（149 行，async，返回 `list[SearchResult]`，干净无流式）：
   `@opik.track`，`input=query`，`output=命中 doc/path/score 摘要`，`tags=["retrieval"]`，metadata 带 `top_k`、`doc` 过滤。

2. **意图识别** — [backend/app/intent/recognizer.py](backend/app/intent/recognizer.py) 的 `IntentRecognizer.recognize()`（46 行，返回 `IntentBatch`）：
   `@opik.track`，`output=intent_type 列表`，metadata 带 `used_llm`。（本轮虽聚焦检索，意图埋点成本极低，顺手补上以便后续做意图准确率。）

3. **生成** — [backend/app/agent/manual_agent.py](backend/app/agent/manual_agent.py) 的 `stream_answer()`（20 行，**async 生成器**）：
   生成器不适合直接 `@opik.track`（会把每个 yield 片段当 output，噪音大）。改用 `opik.start_as_current_span` 上下文：进入时记 `input=system+messages`，`async for` 结束后记 `output=full_text` 与 metadata（`model`、耗时、字符数）。落点选在 [chat_service.py](backend/app/services/chat_service.py) `_answer_flow`（180 行）生成段，或 `stream_answer` 内部包一层，推荐在 `_answer_flow` 处包装（已拿到 `full_text`）。

父 trace 层：`ChatService.handle_chat`（63 行）可选加 `@opik.track`，把 session_id / rag_mode / doc_filter 作为 tags，使一轮对话形成完整 trace 树。

> 说明：`@opik.track` 原生支持 async 函数。所有埋点包在 `opik_enabled` 开关之后（未启用时直接走原逻辑），保证 CI（`pytest`）与 Opik 停机时零影响。

**新建** [backend/eval/golden_dataset.json](backend/eval/golden_dataset.json)，作为评测数据源（复制现有 10 问并补 `reference`）：

```json

  {
    "question": "学生如何进行签到签退？",

    "expect_path_contains": "学生管理",
    "reference": "……人工撰写的参考答案（用于 context_recall / 后续 answer_correctness）……"
  }
]
```

- 保留原 [tests/eval_questions.json](backend/tests/eval_questions.json) 不动（回归测试继续用），避免破坏 [test_retriever.py](backend/tests/test_retriever.py)。
- `reference` 字段本轮用于 `context_recall`（判断检索上下文是否覆盖参考答案要点），后续做生成质量时可复用于 `answer_correctness`/`faithfulness`。

## Part E — 离线评测脚本（检索质量）

**新建目录 `backend/eval/`**，包含：

1. `backend/eval/llm.py` — judge LLM 与 embedding 适配器：
   - judge LLM：Ragas `llm_factory("openai", model=settings.llm_model, base_url=settings.llm_base_url, api_key=settings.llm_api_key)`（复用 DeepSeek）。
   - embedding：`RagasBgeEmbeddings` 自定义类，内部包 `SentenceTransformer(settings.embed_model_name)`，供 `context_recall` 做句向量相似度（复用现有 BGE，不额外下载模型）。

2. `backend/eval/metrics.py` — 指标定义：
   - **确定性指标（纯 Python，零 LLM 成本）**：`recall@k`/`hit@k`（top-k 是否命中 `expect_doc` + `expect_path_contains`）、`MRR`（首个命中排名的倒数）、`precision@k`、相似度分布统计。
   - **LLM 判断指标**：Ragas `context_precision`（judge 评估每条检索切片与问题的相关性排序）、`context_recall`（judge 判断检索上下文是否覆盖 `reference` 要点）。

3. `backend/eval/run_retrieval_eval.py` — 编排入口（CLI）：
   - 读 `golden_dataset.json` → 逐题调 `retriever.search(question, top_k=8)` → 算确定性指标 + Ragas 指标。
   - 用 `opik.evaluation.evaluate(dataset=..., task=..., scoring_metrics=[...])` 把每题输入/输出/分数写入 Opik **Experiment**，支持多轮版本对比。
   - Ragas 指标通过 Opik 官方集成 `from opik.integrations.ragas import ragas_tracker` 作 callback，把 Ragas 打分也落到 Opik trace。
   - 运行方式：`cd backend && python -m eval.run_retrieval_eval`（或 `uv run`，见风险节）。

## 验证方式（端到端）

1. **Opik 起服务**：`docker compose up -d`（官方 compose）→ 浏览器打开 `http://<host>:5173` 能看到空项目 `manual-rag`。
2. **运行时埋点**：`.env` 设 `OPIK_ENABLED=true` + `OPIK_URL`，`uvicorn app.main:app` 启动后发一条 `/chat` 请求（可用前端或 curl）→ Opik UI 的 Traces 里出现该会话的完整 trace 树（intent → retrieve → generate），含检索命中 doc/path/score 与生成耗时。
3. **离线评测**：`cd backend && python -m eval.run_retrieval_eval` → Opik UI 的 Experiments 里出现本次 run，能看到每题 `context_precision`/`context_recall` 分数与 recall@k/MRR。
4. **无回归**：`pytest tests/test_retriever.py` 仍通过；`OPIK_ENABLED=false`（默认）时，`pytest tests/` 全部通过且不连 Opik。
5. **关闭验证**：停掉 Opik 容器后，后端仍能正常 `/chat`（埋点降级告警、不影响业务）。

## 风险与注意事项

| 风险 | 应对 |
|---|---|
| Ragas 在 Python 3.13 装不上（NumPy wheel） | 独立 `uv venv -p 3.12` 跑 eval；或检索质量层改用 Opik 原生 `ContextPrecision`/`ContextRecall`（无 Ragas 依赖），改动仅 `metrics.py` 一处 |
| Opik 与现有 compose 端口冲突（MySQL/Redis） | 独立 compose 项目 + 容器网络隔离，只暴露 UI/API 端口 |
| 埋点影响线上性能/稳定性 | `opik_enabled` 开关 + `try/except` 降级；检索/生成埋点仅包一层，不改业务 |
| judge LLM 用 DeepSeek 产生额外 token 成本 | 确定性指标（recall@k/MRR）零成本先行；LLM 指标仅 10 题，可控；可加采样开关 |
| `.env` 明文密钥（现有问题） | 新增 `opik_api_key` 保持自托管可留空；提醒不要提交 `.env` |
