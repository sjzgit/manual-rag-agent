# 会话记忆：关联手册优先检索

> 版本：v2.0　日期：2026-09-01（v1「全文直答」方案已废弃，原因见 §1）
> 关联实现：`backend/app/services/chat_service.py`、`backend/app/rag/retriever.py`、`backend/app/services/session_service.py`
> 关联迁移：`sql/migrations/V008__sessions_add_memory_docs.sql`（沿用）、`sql/migrations/V010__prompt_revert_memory_direct_answer.sql`（回退 v1 提示词）

---

## 1. 背景与 v1 → v2 演进

一个会话通常围绕某一个功能的操作手册展开。会话记忆的目标：会话首次命中某操作手册后，把该**文档 id** 记入会话记忆（上限 3 个），后续提问利用该上下文提升检索准确率。

**v1「全文直答」（已废弃）**：意图识别注入关联手册全文判断能否直答，可直答则跳过检索、全文作上下文生成。问题：

1. **两次全文注入**：意图小模型 + 生成主模型各注入一次，手册全文动辄数万字，token 成本与首字延迟反噬收益；
2. **职责错位**：「能否直答」塞进意图识别，意图阶段本应只做无关判断/三要素补全/指代消解；
3. **质量风险**：整本手册注入后漏看、误答、引用不精确概率升高——「同一本手册」不代表「问题就在上次命中的段落里」。

**v2「关联手册优先检索」（当前方案）**：保留记忆，取消直答；把记忆作为检索阶段的**优先范围**而非唯一范围——范围内命中分数达标直接采用，不足自动扩展全库；回答始终只注入最终命中的切片。

```
用户提问（照常意图识别，不注入任何记忆内容）
  → 读取 sessions.memory_docs（doc_id 列表，≤3）→ 映射为手册名列表
  → 逐子问题两段式检索：
      先在关联手册范围内混合检索（doc in [...] 过滤）
      ├─ 命中分数 ≥ memory_direct_score_threshold → 直接采用（scope=memory）
      └─ 不足 → 自动全库检索（step 提示「关联手册命中不足，转全库检索」，scope=global）
  → 主模型只用最终命中的父/子切片作答（与普通检索完全一致）
  → 检索作答后：把本次命中文档 id 合并进 sessions.memory_docs（去重、上限 3、不淘汰）
```

## 2. 关键设计决策

### 2.1 存 id 不存内容（沿用 v1）

`sessions.memory_docs` 仅存 `doc_id` 数组（JSON 列），每轮按 id 反查手册名（`KnowledgeService.get_document`，≤3 行主键查询，不做缓存）。文档被删除后 id 解析不到名称 → 跳过该 id，自然退化全库检索；同名重传生成新 id，旧 id 同样失效。**任何阶段都不再读取手册全文**。

### 2.2 意图识别回归三职责

意图识别恢复为：无关判断、三要素补全、指代消解。不接收记忆内容、不输出 `memory_answer_docs`（v1 字段已删除）。历史消息注入保持全量（沿用既有行为）。

### 2.3 范围是「优先」而非「唯一」

- 范围内检索与全库检索走完全相同的混合管线（稠密+稀疏+RRF 融合+阈值过滤+父去重+重排），只是 Milvus expr 多了 `doc in [...]` 过滤；
- 分数达标（`_memory_reliable`）才采用范围结果：final_hits 中至少一条 `score ≥ memory_direct_score_threshold`（rerank 后 score 即 rerank_score，0~1 量纲；未配置 rerank 时为相似度分，量纲不同但方向保守——分数不足只会多走一次全库检索，不会误放行弱命中）；
- 默认阈值 0.6 高于基础 `score_threshold`（0.4），防止「问题已漂移到其他手册」时被范围内的边缘命中锁死。

### 2.4 每个子问题独立判定

多子问题各自独立做「范围优先 → 不足转全库」，天然支持混合来源（部分子问题用关联手册命中、部分全库命中），无 v1 整体判断的粒度问题。

### 2.5 显式文档过滤优先

用户在前端显式指定手册（`ChatRequest.doc`）时，`doc` 精确过滤照常生效，与记忆范围互不干扰（`docs` 与 `doc` 同时传时检索层以 `docs` 优先，编排层只在无记忆时不传 `docs`，显式过滤路径不受影响）。

### 2.6 功能开关

`.env` 配置 `MEMORY_DIRECT_ANSWER`（默认 `true`，`backend/app/core/config.py` 的 `memory_direct_answer`）：

- 开关在**记忆读取**处生效：关闭时 `_memory_doc_names` 直接返回 `[]`，检索永远全库，其余环节无需感知；
- 关闭期间检索后仍正常记录 `memory_docs` 关联（`_remember_docs` 不受开关控制），重新打开时记忆已就绪。

## 3. 数据与实现

### 3.1 数据库（V008 迁移，沿用不变）

```sql
ALTER TABLE sessions
  ADD COLUMN memory_docs JSON NULL
  COMMENT '会话关联的操作手册文档id列表（上限3个，仅存id不存内容）' AFTER clarify_state;
```

- 读取：`SessionService.get_memory_docs(session_id)`，空/无记录返回 `[]`；
- 写入：`SessionService.save_memory_docs(session_id, doc_ids)`，与已有值按序去重合并、`[:3]` 截断（保留先到的 3 个，不淘汰）。

v1 的 Redis `docmd:{doc_id}` 全文缓存（`get_doc_content`/`set_doc_content`、`doc_md_cache_ttl_seconds` 配置）已删除——不再读取全文，无缓存需求。

### 3.2 检索层（backend/app/rag/retriever.py）

- `search(query, doc=None, top_k=None, docs=None)` / `search_and_rerank(query, doc, reranker, top_n, docs=None, scope="global")` 新增 `docs`（手册名列表）与 `scope` 参数；
- `_doc_expr(doc, docs)` 统一构造 Milvus 表达式：列表 → `doc in ["a", "b"]`（元素转义），单值 → `doc == "a"`，稠密/稀疏两路共用；
- `HybridSearchOutcome.scope`（`global` | `memory`）记录本次检索范围，供 step 展示与排查；
- agentic 工具 `search_manual` 不接 `docs`（Agent 自主检索，不预设范围）。

### 3.3 编排层（backend/app/services/chat_service.py）

| 环节 | 方法 | 说明 |
| --- | --- | --- |
| 读记忆 | `_memory_doc_names(session_id)` | 开关开时读 `memory_docs` 并逐 id 反查手册名；失效 id 跳过 |
| 两段式检索 | `_answer_flow` 循环内 | 先 `search_and_rerank(docs=记忆名, scope="memory")`；`_memory_reliable` 不达标 → step「关联手册命中不足，转全库检索」→ 全库重检 |
| step 展示 | 检索 step | 范围命中时标题加「（会话关联手册内）」；detail 恒带 `scope` 字段；retrieval_logs 只落最终采用段 |
| 写记忆 | `_remember_docs`（不变） | 检索作答后 `doc_name → doc_id` 映射合并进 `memory_docs`（上限 3） |

生成阶段（`_generate_generic`/`_finalize_answer`）不感知记忆：上下文就是最终命中的切片，来源卡片为切片级条目。

## 4. 提示词

无新增提示词。v1 的 `memory_answer_system`（直答模板）已从代码 `_DEFAULTS` 与数据库删除（V010 迁移），`intent_system` 恢复三职责版本（无 memory_answer_docs 规则节与输出字段）。

## 5. 边界情况

| 场景 | 行为 |
| --- | --- |
| 关联文档被删除/重传 | id 反查不到手册名 → 跳过该 id；全部失效则无范围，纯全库检索 |
| 范围内命中分数不足 | step 提示转全库，全库重检后作答（范围段结果不落库不透出） |
| 会话已关联 3 个文档后再命中新文档 | 不再关联（保留先到的 3 个，不淘汰） |
| 意图小模型未配置（规则降级） | 与记忆无关，照常全库检索（记忆功能不受影响，优于 v1 的自动关闭） |
| MySQL 不可用 | `get_memory_docs` 返回 `[]`，纯全库检索，链路不受影响 |
| 旧只读知识库文档 | 无 `source_documents` 记录 → 不记入会话记忆（命中 `hit.doc` 无法映射 doc_id） |
| 开关关闭 | 不读记忆，始终全库；记忆仍持续累积 |

## 6. 测试与验证

单测（`backend/tests/test_chat.py`）：

- `test_memory_scope_first_then_global_on_low_score`：范围内低分 → 两次检索（第一次带 docs+scope）、转全库 step、采用全库结果、retrieval_logs 只落最终段；
- `test_memory_scope_hit_uses_memory_result`：范围内高分 → 仅一次检索且带 docs、step 标注「会话关联手册内」、`_remember_docs` 照常回写；
- `test_memory_scope_switch_off`：开关关 → 不读记忆、单次无 docs 检索；
- `test_memory_scope_all_doc_ids_invalid`：关联 id 全失效 → 退化为单次全库检索。

端到端验证要点：

1. 首问某功能 → 全库检索，DB `sessions.memory_docs` 出现对应 doc_id；
2. 同手册追问 → step 显示「（会话关联手册内）」，retrieval_logs 正常记录（范围内也要检索，只是范围小）；
3. 追问关联手册外的功能 → step 显示「关联手册命中不足，转全库检索」，结果正确；
4. 删除某已关联文档后追问 → 该 id 跳过，正常全库，不报错；
5. `.env` 设 `MEMORY_DIRECT_ANSWER=false` → 行为与无记忆版本完全一致。

## 7. 已知取舍与后续优化方向

- **范围内分数不足时的成本**：多一次全库检索（含重排）。范围内命中是常态、漂移是少数，整体仍优于每轮全库；后续可按范围命中率监控调阈值；
- **记忆 chunk 级**：仅记 doc 级。后续可在 `memory_docs` 之外记录最近命中 chunk_id/path，用于连续追问的模块级优先命中（需评估切片失效维护成本）；
- **agentic 模式**：Agent 工具检索不接记忆范围（自主决定检索），后续如需可在 `search_manual` 工具透传 `docs`。
