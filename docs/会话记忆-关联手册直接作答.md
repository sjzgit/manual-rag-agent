# 会话记忆：关联手册直接作答

> 版本：v1.0　日期：2026-09-01
> 关联实现：`backend/app/services/chat_service.py`、`backend/app/intent/recognizer.py`、`backend/app/services/session_service.py`、`backend/app/services/cache.py`
> 关联迁移：`sql/migrations/V008__sessions_add_memory_docs.sql`、`sql/migrations/V009__prompt_memory_direct_answer.sql`

## 1. 背景与目标

一个会话通常围绕某一个功能的操作手册展开。当前系统每次提问都走完整链路：意图识别（独立小模型）→ 逐子问题混合检索（稠密+稀疏+重排）→ 主模型流式生成。用户在会话内围绕同一操作手册连续追问时，重复检索同一文档是浪费。

目标：会话首次命中某操作手册后，把该**文档 id** 记入会话记忆（上限 3 个），下次提问若仍在已关联文档范围内，则**跳过检索**、直接拿文档内容作答，提升问答效率、节省频繁检索。

**核心设计原则**：会话记忆只存 `doc_id`、不存内容——作答时按 doc_id 实时读取 md 文件内容，避免文档内容变更或被删除后会话中还保留历史文档内容；md 内容加短期 Redis 缓存，避免频繁读文件。

## 2. 整体流程

```
用户提问
  → 读取 sessions.memory_docs（doc_id 列表，≤3）
  → 按 doc_id 加载关联文档完整内容（Redis 短期缓存优先，未命中读 md 文件并回写；文档已失效则跳过）
  → 意图识别（system prompt = 基础意图提示词 + 「会话记忆文档内容」分隔块）
      LLM 对每个 precise 子问题额外输出 memory_answer_docs（可直接作答的文档名称列表）
  → 全部 precise 且每个子问题都有覆盖文档？
      是 → 记忆直答：跳过检索，用关联文档完整内容作上下文，主模型流式生成
             └─ 生成时 LLM 判定依据不足？→ 输出 [[NEED_RETRIEVAL]] 标记 → 回退检索流程重新作答
      否 → 原检索流程：逐子问题混合检索 → 生成回答
  → 检索作答后：把本次命中文档 id 合并进 sessions.memory_docs（去重、上限 3、不淘汰）
```

三步拆解：

1. **记**（`_remember_docs`）：检索作答后，把最终命中来源涉及的文档名经 `doc_name → doc_id` 映射，合并进 `sessions.memory_docs`（去重、上限 3、超过不再关联）。
2. **判**（意图识别扩展）：把关联文档的完整内容注入意图识别 system prompt，小模型在输出意图的同时，对每个 precise 子问题输出 `memory_answer_docs`（能否凭这些文档直接作答 + 覆盖文档名称列表）。
3. **答**（`_answer_from_memory`）：若全部子问题都可直答，跳过检索，按意图输出的文档名筛选文档内容拼上下文，走主模型流式生成；生成阶段依据不足时自动回退检索。

## 3. 关键设计决策

### 3.1 存 id 不存内容

- `sessions.memory_docs` 仅存 `doc_id` 数组（JSON 列）；
- 每轮意图识别前按 doc_id 实时取 md 内容（`uploads/{doc_name}/{doc_name}.md`）；
- 文档被重传（同名覆盖生成新 doc_id）或删除后，旧 id 自然失效，加载时跳过，不会把陈旧内容注入上下文；
- Redis 缓存 key 为 `docmd:{doc_id}`，TTL 默认 300 秒（`doc_md_cache_ttl_seconds`），短 TTL 天然规避内容变更后的陈旧缓存。

### 3.2 意图识别负责"判"，主模型负责"答"

直接作答的判断（路由决策）放在意图识别阶段，由小模型完成；最终答案仍由主模型（`llm_*` 配置）在生成阶段流式产出：

- 保留流式体验（token/reasoning 逐段推送）与主模型的答案质量；
- 意图识别仍是"分类 + 路由"（小模型干小活），生成仍是"产出答案"（主模型），职责清晰；
- 省掉的是链路中最贵的混合检索环节。

意图识别输出新增字段（每个子问题）：

```json
"memory_answer_docs": ["实验会议室预约操作手册"]
```

- 能仅凭关联文档完整、准确回答 → 填覆盖该问题的文档名称列表（须与注入的文档名完全一致）；
- 超出范围或内容不足 → 空数组 `[]`；
- 无关联文档内容注入时恒为空数组；`irrelevant` / `vague` 恒为空数组。

### 3.3 整体判断（v1 简化）

一次提问可能拆成多个子问题。v1 采用**整体判断**：只有全部 precise 子问题都输出非空 `memory_answer_docs` 时才跳过检索；任一子问题需检索则整体走检索。不做子问题级的"部分直答 + 部分检索"混合（后续可优化）。

### 3.4 生成阶段兜底：NEED_RETRIEVAL 回退

意图识别的判断基于文档名/内容范围，可能误判"可直答"。记忆直答使用专用回答提示词（`memory_answer_system`，存 `prompt_templates` 表），明确要求：

> 如果【参考文档】不足以回答用户问题，不要强行回答，只输出 [[NEED_RETRIEVAL]]（不输出任何其他内容），系统会转为检索流程重新作答。

编排层流式检测该标记（`chat_service._answer_from_memory`）：

- **首段缓冲**：内容仍是标记前缀时暂不下发，一旦与标记发散立即放行缓冲内容、恢复流式输出——正常直答的首 token 延迟只有标记长度量级；
- 命中完整标记 → 关闭底层流（归还 httpx 连接）→ 转 `_answer_flow` 检索后重新生成，标记不透出给用户；
- 回退后本轮答案、来源卡片、落库与普通检索路径完全一致。

### 3.5 功能开关

`.env` 配置 `MEMORY_DIRECT_ANSWER`（默认 `true`，`backend/app/core/config.py` 的 `memory_direct_answer`）：

- 开关在**意图识别阶段**生效：关闭时不加载、不注入关联文档内容（`chat_service.py` 中 `if self.sessions and self.settings.memory_direct_answer` 才读取 memory_docs）；
- 意图识别 prompt 无记忆内容 → `memory_answer_docs` 恒为空 → `answer_docs` 为空 → 自然走检索流程，后续环节无需感知开关；
- 关闭期间检索后仍正常记录 `memory_docs` 关联（`_remember_docs` 不受开关控制），重新打开时记忆已就绪。

### 3.6 降级路径自动关闭

意图识别的**规则降级路径**（`used_llm=False`，未配置意图小模型时）不输出 `memory_answer_docs`（恒为空数组）——记忆直答自动关闭、回退检索，无需额外分支。

## 4. 数据与缓存

### 4.1 数据库（V008 迁移）

```sql
ALTER TABLE sessions
  ADD COLUMN memory_docs JSON NULL
  COMMENT '会话关联的操作手册文档id列表（上限3个，仅存id不存内容）' AFTER clarify_state;
```

- 读取：`SessionService.get_memory_docs(session_id)`，空/无记录返回 `[]`；
- 写入：`SessionService.save_memory_docs(session_id, doc_ids)`，与已有值按序去重合并、`[:3]` 截断（"超过 3 个不再关联" = 保留先到的 3 个，不淘汰）。

### 4.2 Redis 文档内容缓存

`RedisService`（`backend/app/services/cache.py`）：

- `get_doc_content(doc_id)` / `set_doc_content(doc_id, doc_name, content, ttl=None)`；
- key：`docmd:{doc_id}`，值为 `{"doc_name":..., "content":...}` JSON；
- TTL 默认 300 秒（`DOC_MD_CACHE_TTL_SECONDS`）；Redis 未配置时直通降级（每次读文件）。

### 4.3 doc_name → doc_id 映射

检索命中的 `hit.doc` 是文档名，`KnowledgeService.get_document_id_by_name(doc_name)` 按 `source_documents.doc_name`（唯一键）反查 id。旧只读知识库（`chunks.json`/`media_root`）文档在 `source_documents` 无记录 → 返回 None → 不记入记忆（仅管理端上传的文档可关联，符合"存 id"前提）。

## 5. 提示词（存 prompt_templates 表，V009 迁移）

| key | 名称 | 用途 |
| --- | --- | --- |
| `intent_system` | 意图识别提示词 | 新增「会话记忆直接作答（memory_answer_docs）」判断规则与输出字段说明；运行时由 `_memory_context_prompt` 在末尾追加「## 会话记忆文档内容」分隔块 |
| `memory_answer_system` | 会话记忆直答提示词 | 直答专用回答模板：严格基于【参考文档】、依据不足只输出 `[[NEED_RETRIEVAL]]`、图片链接原样保留、末尾附来源（文档级） |

注入格式（意图识别 system prompt 末尾追加）：

```
## 会话记忆文档内容（本会话已关联的操作手册完整内容，仅供判断能否直接作答）

### {doc_name}

{content}

---

### {doc_name_2}
...
```

## 6. 编排细节（chat_service.py）

| 环节 | 方法 | 说明 |
| --- | --- | --- |
| 加载记忆 | `_load_memory_doc_contents(doc_ids)` | 逐 id：Redis 优先 → 未命中经 `KnowledgeService.get_document_path(doc_id,"md")` 读文件回写 Redis；文档失效跳过。返回 `[{doc_id, doc_name, content}]` |
| 意图识别 | `recognize(question, history, memory_docs)` | memory_docs 经 `_memory_context_prompt` 注入 system prompt |
| 直答分支 | `answer_docs = [d for d in memory_docs if d.doc_name in batch.memory_answer_docs]` | 按意图输出的文档名筛选（全部子问题可直答才进入） |
| 直答生成 | `_answer_from_memory` | step 提示「命中会话记忆，跳过检索」→ 专用 system prompt → 流式生成 + 标记检测 → 兜底回退或正常收尾 |
| 检索回退 | `_answer_flow` | 与普通检索一致；结束后 `_remember_docs` 更新记忆 |
| 收尾共用 | `_finalize_answer` | 日志、LLM 调用落库、来源卡片、assistant 消息持久化（检索/直答共用） |

记忆直答的来源卡片为**文档级**条目（`chunk_id=doc_id`、`doc=doc_name`、`path=doc_name`、`score=1.0`），无切片级 content。记忆直答固定走 generic 生成（固定上下文），不走 agentic（agentic 会自行再检索，违背跳过检索的目的）。

## 7. 边界情况

| 场景 | 行为 |
| --- | --- |
| 关联文档被删除/重传 | `_load_memory_doc_contents` 取不到 md 路径 → 跳过该 id；全部失效则 memory_docs 为空 → 走检索 |
| 会话已关联 3 个文档后再命中新文档 | 不再关联（保留先到的 3 个，不淘汰） |
| 意图小模型未配置（规则降级） | `memory_answer_docs` 恒为空 → 自动回退检索 |
| 直答时主模型判定依据不足 | 输出 `[[NEED_RETRIEVAL]]` → 关闭流、转检索流程重新作答，标记不透出 |
| Redis 未配置 | 文档内容缓存直通降级，每轮直接读 md 文件（功能不受影响） |
| MySQL 不可用 | `get_memory_docs` 返回 `[]`，记忆直答关闭，链路不受影响 |
| 旧只读知识库文档 | 无 `source_documents` 记录 → 不记入会话记忆 |

## 8. 测试与验证

单测（`backend/tests/test_chat.py`）：

- `test_memory_direct_answer_skips_retrieval`：意图输出 `memory_answer_docs=["手册A"]` → 不调检索、来源卡片为文档级条目（`chunk_id=doc_id`）；
- `test_memory_answer_marker_falls_back_to_retrieval`：直答流输出 `[[NEED_RETRIEVAL]]` → 回退检索、标记不出现在用户可见输出；
- `test_memory_insufficient_falls_back_to_retrieval`：意图未输出可直答文档 → 正常检索。

端到端验证要点：

1. 首问某功能 → 走检索，DB `sessions.memory_docs` 出现对应 doc_id，`retrieval_logs` 有记录；
2. 同一文档内追问 → 日志显示无新增 `retrieval_logs`，Redis 出现 `docmd:{id}`，step 显示「命中会话记忆，跳过检索」；
3. 换到另一文档提问 → 回到检索，`memory_docs` 增加第二个 doc_id；
4. 连问覆盖 4 个不同文档 → `memory_docs` 恒为 3；
5. 删除某已关联文档后追问 → 跳过该 id 回退检索，不报错、不输出陈旧内容；
6. `.env` 设 `MEMORY_DIRECT_ANSWER=false` → 全部走检索，直答逻辑不触发。

## 9. 已知取舍与后续优化方向

- **意图识别 token 成本**：每轮注入最多 3 本手册全文，意图小模型输入成本显著上升（换取判断精确性）。若成本敏感，可评估改为只注入文档名清单（范围判断）或将判断收敛到生成阶段一次完成；
- **子问题级混合直答**：v1 整体判断，部分可直答时全部走检索；后续可做子问题级路由（直答子问题用记忆、其余检索后合并上下文）；
- **超大手册全文注入**：上限 3 个文档已封顶最坏情况，单文档超长时可考虑按子问题要素（module）筛选相关章节注入。
