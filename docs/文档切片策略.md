# 切片策略

> **v2.0 父子切片改造方案**（子切片检索 + 父级组织上下文）见文末「七、父子切片方案」，已实现；v2.1 起父/子切片层级**按文档内容动态探测**，不再固定 H3/H4。

### 核心原则

| 原则 | 说明 |
|------|------|
| **功能边界优先** | 以 H3 标题（`###`）对应的功能模块为最小切片单元 |
| **上下文完整** | 每个切片包含从根模块到当前模块的完整面包屑路径 |
| **图片原位保留** | 图片 `![](path)` 引用保留在切片文本中，不单独向量化 |
| **小模块合并** | 文本量不足 150 字符的相邻功能模块自动合并，避免碎片化 |
| **大模块拆分** | 文本量超过300字的模块按照子级再次拆分分片，比如：H3模块超过300字，则按照H4模块再拆分 |

### 切片规则

```
文档标题 (#)
├── H2 (##)      一级模块 — 不单独切片，作为上下文路径
│   ├── H3 (###)   二级功能 — 切片单元
│   │   ├── H4 (####) 子功能 — 合并回父 H3，不独立切片
│   │   └── ...
│   ├── H3 合并  同级 H3 文本量 < 150 字符时自动合并
│   └── ...
└── ...
```

**规则详解**：

1. **H3 为切片主体** — Markdown 的三级标题（`###`）对应一个完整的功能操作，如「新增预约申请」「审核」「门禁绑定」等。
2. **H4 合并入 H3** — 四级标题是 H3 下的子页面（如 H3「首页」下的 H4「体检/体测」），内容少，合并到父 H3 中。
3. **兄弟合并** — 同一 H2 下，连续多个 H3 的纯文本（不含图片）少于 150 字符时，合并为一个切片，避免「操作系统要求」「浏览器要求」等零碎信息各自独立。
4. **面包屑注入** — 每个切片首行注入 `## H2 > H3` 格式的路径，Agent 可直接引用精确定位。

### 2.3 不向量化的内容

| 内容 | 处理方式 | 原因 |
|------|---------|------|
| 图片本身 | 仅保留 `![](path)` 文本引用 | 图片不参与语义检索，Agent 按需引用展示 |
| 免责声明/版权声明 | 已从源文档删除 | 与功能操作无关 |
| 文件修改记录 | 已从源文档删除 | 历史元数据，非操作知识 |
| 阅读对象 | 已从源文档删除 | 非操作内容 |

## 切片保存表结构

| 字段 | 类型 | 说明 | 示例 |
|------|------|------|------|
| `id` | string | 唯一标识，切片id |  |
| `doc` | string | 所属源文档id，关联源文档表中的文档id |  |
| `path` | string | 面包屑路径，` > ` 分隔，从一级模块到当前功能 | `"河南实验会议室 > 会议室预约审核"` |
| `level` | int | 路径层级深度（2 = H2 > H3，合并后可能更浅） | `2` |
| `chunk_index` | int | 该文档内的切片序号（从 0 开始） | `0` |
| `content` | string | **切片正文**，包含面包屑标题 + 操作步骤文本 + 图片引用，**这是实际送入向量化的内容** | 见下方示例 |

| `has_images` | bool | 是否包含图片引用 | `true` |
| `image_count` | int | 包含的图片数量 | `18` |
| `vector_state` | string | 切片对应的向量化状态 | 规定几个状态：`pending` `success` `failure` |
| `vertor_id` | string | 对应存到向量数据库中的向量数据id |  |

## 六、使用方式

### 6.1 向量化

将每个切片的 `content` 字段送入 Embedding 模型：

```python
import json

with open("chunks.json", "r", encoding="utf-8") as f:
    chunks = json.load(f)

texts = [chunk["content"] for chunk in chunks]
# texts → Embedding Model → 向量数据库
```

### 6.2 检索后引用图片

Agent 检索到切片后，通过切片中保留的 `![](./media/xxx.png)` 引用，向用户展示对应的操作截图：

```python
# 检索命中后
matched = chunks[3]
# 回答中引用：
answer = f"{matched['content']}"
# 图片路径相对于 处理后的md手册文档/{doc}/media/
```

### 6.3 元数据过滤

可利用 `doc`、`path` 字段实现按文档或模块过滤：

```python
# 仅搜索「会议室」相关
filtered = [c for c in chunks if "会议室" in c["path"]]
```

# 七、父子切片方案（v2.0，已实现）

> **状态**：已实现。v2.1 起父/子切片层级**按文档内容动态探测**（见 7.2/7.3），不再固定 H3/H4，解决文档标题层级不齐（如「积点评价操作手册」全篇上移一级、仅到 H2）导致的子切片丢内容问题。

### 7.1 设计动机：单层补丁 → 双层解耦

现行 v1.x 的三条规则，本质是给**同一层切片**打补丁——单层切片必须同时满足「检索要准」与「上下文要全」两个矛盾目标：

| 现有规则 | 解决的问题 | 牺牲的一方 |
|------|------|------|
| H4 合并回 H3 | 上下文完整 | 检索精度（一个向量要代表多个子功能） |
| 兄弟合并（< 150 字符） | 避免碎片化 | 检索精度（整块返回，可能答非所问） |
| 大模块拆分（> 300 字按 H4 拆） | 检索精度 | 上下文完整 |

父子切片（Small-to-Big）把**检索单元**与**上下文单元**解耦为两层，上述三条补丁规则全部退场，由结构本身解决：

- **子切片**：小而准，负责向量检索命中；
- **父切片**：完整功能模块，负责命中后组装 LLM 上下文。

### 7.2 层级映射：动态探测模块层级

父/子切片的层级**不再固定 H3/H4**，而是由文档实际内容动态探测。通用结构如下，其中「模块层级」由算法确定：

```
文档标题 (#)                — 首个标题，直属正文（封面/目录）丢弃
├── 容器层（可能多层）        — 无直属正文的标题，仅作面包屑路径
│   ├── ★ 模块层级（动态）     — 父切片（上下文单元，不向量化）
│   │   ├── 模块的下级标题      ★ 子切片（检索单元，向量化）
│   │   ├── 段落/步骤组         ★ 子切片 — 模块无下级标题时按语义段切分
│   │   └── ...
```

**模块层级探测规则**：对每个标题层级 L，统计该层节点的「直属内容权重」= 直属纯文本字符数 + 图片数 × 50（`IMG_WEIGHT`）；取权重最大的层级为模块层级，并列时取更深层级。功能模块正是「操作步骤正文 + 截图」聚集的层级，据此可稳定识别。

四份文档的探测结果：

| 文档 | 标题结构 | 探测出的模块层级 |
|------|------|------|
| 上体附中系统操作手册 | `# → ## → ### → ####` | H3 |
| 实验会议室预约操作手册 | `# → ## → ###` | H3 |
| 文创小铺操作手册 | `# → ## → ###` | H3 |
| 积点评价操作手册 | 标题整体上移一级（功能在 H2，仅两处 H3） | **H2** |

> 退化特性：即便极端文档里模块层全无直属正文、导致权重误判到更深一层，结果也只是父切片更细颗粒，**绝不丢内容**——这是与固定层级方案的本质区别。

### 7.3 切片规则

**父切片（上下文单元）**：

1. 以**动态探测出的模块层级**为单位生成，**不再做任何合并/拆分** —— 兄弟合并、大模块拆分两条规则废除；
2. 保留完整面包屑、操作步骤、全部图片引用；
3. 不送 Embedding、不入 Milvus，仅存于 JSON / 数据库层。

**遍历规则（按相对层级递归）**：

| 节点类型 | 判定条件 | 处理 |
|------|------|------|
| 标题节点 | 首个标题且层级浅于模块层 | 直属正文（封面/目录）丢弃，不入片 |
| 模块节点 | 层级 == 模块层 | 生成父切片 + 子切片 |
| 错位模块 | 层级浅于模块层、但有直属正文/图片 | 按模块处理：生成父切片（面包屑仅含自身标题）+ 语义段子切片 |
| 容器节点 | 层级浅于模块层、无直属正文 | 不切片，仅并入面包屑后递归子节点 |
| 深层节点 | 层级深于模块层 | 整体并入其最近祖先子切片 |

> **错位模块**是关键修复点：如「积点评价操作手册」的 `# 2、业务流程`（仅一张流程图）、`# 3、角色权限`（一张权限表），层级虽浅于模块层但自身带内容，必须成片，否则内容丢失。

**子切片（检索单元）**，按优先级依次应用：

1. **模块有下级标题** → 每个直接子标题独立成子切片（更深一级的层级递归折叠进来）；模块直属引言段落并入首个子片；
2. **无下级标题** → 按语义段落 / 操作步骤组分段，目标区间 **100 ~ 300 字符**（bge-base-zh-v1.5 对该量级中文短文本区分度最佳；低于 50 字符的段落并入相邻片）；
3. **每个子切片首行重注入面包屑** `## 容器 > 模块`（有下级标题时 `## 容器 > 模块 > 子标题`）—— 子切片脱离父级后仍能被正确语义定位的关键；
4. **图片跟随所在段落进入子切片**：embedding 前仍走 `clean_for_embedding`（图片引用替换为 `[图片：alt]`）去路径噪声；图片完整性由父切片兜底，子切片丢图无碍。

**规模示例**：最大切片「教师管理（职责管理）」（836 字符 + 12 图）→ 父 = 整个模块；子 ≈ 3 ~ 4 片（按下级标题或步骤组），每片带面包屑约 150 ~ 280 字符。

### 7.4 数据结构改造

`chunks.json` 新增 `chunk_type` / `parent_id`；父 ID 保持 `{doc}_{path}` 不变，子 ID 为 `{父id}::c{child_index}`：

```jsonc
// 父切片
{
  "id": "实验会议室预约操作手册_河南实验会议室_会议室预约审核",
  "chunk_type": "parent",
  "doc": "实验会议室预约操作手册",
  "path": "河南实验会议室 > 会议室预约审核",
  "level": 2,
  "chunk_index": 0,
  "content": "（完整 H3 内容，含全部图片引用）",
  "child_ids": ["实验会议室预约操作手册_河南实验会议室_会议室预约审核::c0"],
  "vector_state": "",
  "vertor_id": ""
}

// 子切片
{
  "id": "实验会议室预约操作手册_河南实验会议室_会议室预约审核::c0",
  "chunk_type": "child",
  "parent_id": "实验会议室预约操作手册_河南实验会议室_会议室预约审核",
  "child_index": 0,
  "doc": "实验会议室预约操作手册",
  "path": "河南实验会议室 > 会议室预约审核",
  "content": "## 河南实验会议室 > 会议室预约审核\n（该段正文）",
  "vector_state": "success",
  "vertor_id": "..."
}
```

切片保存表新增字段：

| 新增字段 | 类型 | 说明 |
|------|------|------|
| `chunk_type` | string | `parent` / `child` |
| `parent_id` | string | 子切片指向父切片 id，父切片为空 |
| `child_index` | int | 子切片在父内的序号（从 0 开始） |

> 注：现有字段 `vertor_id` 为 `vector_id` 拼写笔误，实施 v2.0 时一并修正。`vector_state` / `vector_id` 仅子切片有值。
>
> `level` 为**面包屑路径深度**（`path` 中以 ` > ` 分隔的段数），随模块层级动态计算，不再固定为 2/3。

### 7.5 向量库与检索链路

**Milvus —— 只入子切片**：

1. 新建 collection（如 `manual_rag_child_chunks`）而非原地覆盖，便于新旧对照与回滚；
2. Schema 基本不变，可选加 `parent_id` 标量字段。按现有实现亦可不加：`backend/app/rag/retriever.py` 的 `_raw_chunks` 已是 id→原文映射，扩展一个 `_parents` 字典即可完成子→父回溯（本地内存查表）；
3. FLAT 索引 + 数十至上百条子切片，无性能压力。

**检索流程**（核心变化在 `build_context` 一带）：

```
query
 → ① 向量检索子切片，top_k 提高到 6 ~ 10（检索单元变小，默认 2 会漏）
 → ② score 阈值过滤（沿用 filter_by_threshold，阈值观察后微调）
 → ③ child_id → parent_id 回溯
 → ④ 按 parent_id 去重（同一父的多个命中只保留一次）
 → ⑤ 父排序：按 doc + chunk_index 文档序，而非相似度序
    （手册内容按原文顺序读更连贯；父的展示分数取其子命中最高分）
 → ⑥ 上下文 = 父切片 content 拼接，图片 URL 改写沿用 to_source_chunk
```

第 ④⑤ 步是收益核心：子切片小而准地命中，去重后进入 LLM 的是少量完整功能模块——既不像细切片那样上下文破碎，也不像大切片那样稀释语义。

**代码衔接点**（仅列职责变化）：

| 位置 | 变化 |
|------|------|
| `vector_store/ingest_chunks.py` | 只遍历 `chunk_type == "child"` 入库 |
| `backend/app/rag/retriever.py` 启动加载 | 额外构建 `_parents` 映射 |
| `backend/app/rag/retriever.py` `to_source_chunk` | 图片改写逻辑不变，但作用于**父**内容 |
| `backend/app/rag/retriever.py` `build_context` | 增加「回溯 → 去重 → 文档序排序」三步 |
| `backend/app/rag/retriever.py` `search_manual`（Agent 工具） | 返回子级 `path`（引用定位精确）+ 父级 `content`（内容完整） |

### 7.6 迁移与调参

| 事项 | 说明 |
|------|------|
| **实施顺序** | 改切片脚本产出双层数据 → 建新 collection 入库子切片 → 改 retriever → 真实问题对比新旧命中率与回答完整性 → 切流 |
| **top_k** | `retrieve_top_k` 从 2 提到 6 ~ 10；`score_threshold`（现 0.4）在子切片上分布会变化，观察后微调 |
| **引用粒度** | 前端来源卡片用子切片 `path` 展示命中位置，正文展示父内容——精度与完整性两头兼顾 |
| **文档同步** | 按 `docs/文档切片/README.md` 第八节约定，切片策略与变更记录同步升 v2.0 |

### 7.7 进阶方向（二期）

| 方向 | 说明 |
|------|------|
| **多级回溯** | 同一 H2 下 ≥ 2 个不同 H3 被命中时，上下文升级为整个 H2（层级结构天然支持，加 `grandparent` 查表即可） |
| **邻居扩展** | 命中子切片时把相邻 `child_index` 兄弟片一并带入父上下文，对「下一步怎么做」类连续操作问题友好 |
| **两段式检索** | 子切片最高分仍低于阈值时，降级用父切片全文重新检索（鲁棒性兜底） |
